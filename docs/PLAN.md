# MVA Live Scoreboard implementation plan

**Current phase:** 01E isolated migration rehearsal. **Product status:** In Development. The migration was applied, rolled back, and reapplied only in a separate temporary PostgreSQL cluster with synthetic data; `mva_dev` and production were untouched. No application feature is implemented. See the [runbook](DB_RUNBOOK.md#phase-01e-isolated-rehearsal-results).

## Sequence and gates

Do not start schema or Auth work until the MVA identity boundary and scoreboard project isolation are reviewed. Do not start MVA integration until its actual schema, eligibility policy, and restricted read contract are confirmed. Do not ship score mutations before atomicity, idempotency, correction semantics, and authorization are tested. Do not call the overlay broadcast-ready before real OBS testing.

## Immediate architectural blockers

- Local `mva_dev` is PostgreSQL 18 without `auth` schema, while both repos configure the same external Supabase URL/key. Deployed Auth issuer, domain/session behavior, and shared-schema approval remain unconfirmed.
- MVA schema and `VERIFIED` filtering are verified in source. Proposed scheduling statuses and a restricted catalog endpoint need MVA owner approval and implementation.
- The local target is identifiable, but disposable-clone designation, owner approval, backup/retention period, non-superuser runtime credential, and production rollout approval remain outstanding.
- Proposed best-of-three and operational scoring defaults need MVA association approval; official FIVB rules are identified separately in the architecture review.

**Next bounded task:** Confirm live Auth issuer and login redirects, MVA owner approval for the intended nonproduction integration target, and a non-superuser server credential/mutation boundary. Then implement Auth and database access in a separate bounded phase; the current SQL is guarded against `mva_dev`.
